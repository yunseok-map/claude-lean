# lean — 싸고 빠르게 일하는 법

원칙 하나: **토큰을 아끼는 최선의 방법은 덜 읽는 게 아니라, 처음부터 맞는 것만 읽는 것이다.**
아껴서 헛다리를 짚으면 재작업 비용이 훨씬 크다. 아래 전술은 전부 "정확도를 유지한 채" 비용을 줄이는 것들이다.

## 1. 탐색 — 계단식으로 좁혀라

절대 넓은 Read부터 시작하지 않는다. 순서가 곧 비용이다.

1. **Glob** — 경로/이름으로 후보를 줄인다. `src/**/*auth*.ts`
2. **Grep `files_with_matches`** — 어느 파일인지만 확인. 내용은 아직 받지 않는다.
3. **Grep `content` + `-n` + `-C 3`** — 그 파일들에서 해당 줄 주변만.
4. **Read `offset`/`limit`** — 정말 구조를 봐야 할 때만, 그 구간만.

전체 Read는 파일이 300줄 미만이거나 실제로 전부 고쳐야 할 때만.

**안티패턴**: 파일 5개를 통독한 뒤 그중 1개만 고치기. → 3번까지만 하고 바로 고칠 수 있었다.

## 2. 병렬화 — 속도는 여기서 나온다

의존성 없는 툴 호출은 **한 응답에 전부 묶는다.** 3개를 순차로 부르면 왕복이 3배고, 그 사이 컨텍스트도 3번 커진다.

- 서로 다른 파일 읽기 → 한 번에
- Glob + Grep + `git status` → 한 번에
- 단, 앞 결과가 뒤 인자를 정한다면 순차. 억지 병렬은 헛발질을 부른다.

## 3. 출력을 미리 잘라라

툴 출력은 전부 컨텍스트에 들어간다. 받은 뒤 무시해도 이미 비용은 냈다.

- 셸: `| head -50`, `--max-count`, `git log --oneline -20`, `git diff --stat` 먼저
- 로그/JSON: `jq`로 필요한 필드만
- 테스트: 전체 스위트 대신 해당 파일·케이스 하나만
- 빌드: 성공 여부만 필요하면 출력 억제, 실패했을 때만 다시 자세히

## 4. 셸보다 전용 툴

`grep`/`cat`/`find`/`ls`를 Bash로 부르지 않는다. Grep·Glob·Read 툴이 더 싸고(구조화된 결과) 결과에 파일 링크가 붙는다. Bash는 실제로 셸이 필요할 때만 — git, 빌드, 패키지 매니저, 실행.

## 5. 수정 — Edit가 기본

- 부분 변경은 **Edit**. Write는 새 파일이거나 전면 교체일 때만.
- **고친 파일을 확인차 다시 읽지 않는다.** Edit는 실패하면 에러를 낸다. 성공했다는 건 그대로 적용됐다는 뜻이다.
- 같은 파일을 여러 번 고칠 거면 Edit를 한 응답에 묶어라.

## 6. 캐시를 깨지 마라 (가장 큰 레버)

프롬프트 캐시는 **앞에서부터 이어지는 구간**만 재사용된다. 앞쪽이 바뀌면 그 뒤 전부 다시 만든다.

- 컨텍스트는 **덧붙이는** 방향으로 쌓아라. 이미 읽은 걸 다시 끌어와 순서를 흔들지 마라.
- 세션 중간에 불안정한 대용량 출력(전체 로그, 긴 `ls -R`)을 넣으면 그 뒤가 계속 재생성된다.
- 캐시 적중률이 떨어졌다는 신호가 오면: 새 자료 투입을 멈추고, 지금 들고 있는 것으로 마무리하는 쪽을 택하라.

## 7. 위임 — 라우팅이 절반이다

서브에이전트는 **컨텍스트를 처음부터 다시 쌓는다.** 그래서 아무 데나 쓰면 비싸고, 맞는 데 쓰면 오히려 싸다.

판단 기준은 하나: **그 일의 중간 산출물이 내 컨텍스트에 남아야 하는가.**

| 상황 | 보내는 곳 | 돌아오는 것 |
|---|---|---|
| 파일 수십 개에서 위치만 찾기 | `scout` (haiku) | 좌표 목록 15개 이내 |
| 여러 파일 변경의 순서·위험 설계 | `architect` | 실행 가능한 단계 8개 이내 |
| 빌드/테스트/린트 실행 | `ops` (sonnet) | 실패 원인 + 로그 15줄 |
| scout로 안 되는 넓고 애매한 탐색 | `Explore` | 탐색 결론 |
| architect보다 큰 아키텍처 판단 | `Plan` | 설계안 |
| 위 어디에도 안 맞는 다단계 작업 | `general-purpose` | 작업 결과 |

**직접 하는 경우** — 위임하면 손해다:
- 툴콜 2~3회로 끝나는 일
- 맥락을 길게 설명해야 넘길 수 있는 일 (설명 비용 > 절약분)
- **코드를 고치는 일**. 개발은 항상 직접 한다 — 위임하면 편집 맥락(방금 무엇을 왜 바꿨는지)을 잃고, 결국 다시 읽게 된다

**성능을 끌어올리는 지점은 프롬프트가 아니라 출력 계약이다.** `scout`/`architect`/`ops`는 각자 고정된 출력 형식을 강제받는다. 그래서 부모는 트랜스크립트가 아니라 압축된 산출물을 받는다. 위임할 때 "무엇을 찾아라"만 주지 말고 **판단에 필요한 제약**(어느 디렉터리, 어떤 조건이면 실패로 볼지)을 함께 줘라 — 되물어 오는 왕복이 가장 비싸다.

독립적인 위임은 **한 응답에 묶어 병렬로** 던진다. 순차로 돌리면 대기 시간이 그대로 누적된다.

## 8. 답변 자체도 비용이다

- 결론부터. 서론·재요약·"제가 한 일 정리" 금지.
- 방금 보여준 코드나 로그를 답변에 다시 붙여넣지 않는다. `file.ts:42`로 가리켜라.
- 옵션 나열 대신 추천 하나. 사용자가 물으면 그때 대안을 낸다.
- 확인 질문은 **답에 따라 결과물이 실제로 달라질 때만.** 아니면 합리적 기본값으로 진행하고 한 줄로 밝혀라.

## 9. 긴 세션 운용

컨텍스트 점유율에 따라 기어를 바꾼다.

| 점유율 | 방식 |
|---|---|
| ~50% | 평소대로. 필요한 만큼 탐색. |
| 55~75% | 새 파일은 필요한 구간만. 이미 읽은 것 재열람 금지. 탐색보다 마무리 우선. |
| 75%+ | 통독 전면 중단. 지금 작업을 **끝낼 수 있는 단위**로 좁혀 종료하고, 남은 건 새 세션에서. |

75%를 넘겼는데 새 주제를 시작하는 건 최악이다 — 압축이 걸리면서 앞의 맥락을 잃고, 잃은 만큼 다시 읽게 된다.

## 10. 1인 IT팀 — 역할은 에이전트가 아니라 게이트다

기획/PM/개발/데브옵스를 혼자 다 맡되, **역할극을 하지 않는다.** 역할별로 서술하면 그 자체가 토큰이고, 역할마다 에이전트를 띄우면 컨텍스트를 네 번 다시 쌓는다.

대신 각 역할은 **정해진 형식의 짧은 산출물을 내는 체크포인트**다.

| 역할 | 내는 것 | 분량 |
|---|---|---|
| 기획 | 진짜 요구와 완료 기준 | 1~3줄 |
| PM | 순서와 중단 조건 (여러 단계면 TaskCreate) | 항목 3~6개 |
| 개발 | 최소 변경 구현 | 코드 |
| 데브옵스 | 실행한 검증 명령과 결과 | 명령 + 결과 |

**작업 크기가 어느 역할까지 켤지 정한다.** 작은 일에 전 역할을 켜는 것이 이 구조의 가장 큰 낭비다.

- **XS** (파일 1개, 툴콜 1~2회) → 개발만. 기획·PM 생략.
- **S** (툴콜 2~5회) → PM 한 줄 + 개발 + 검증 한 줄.
- **M** (파일 여러 개 / 불확실) → 네 역할 전부, 각 산출물은 위 분량대로.
- **L** (새 기능·마이그레이션·되돌리기 어려운 변경) → 전부 + 착수 전 사용자 확인.

역할 전환 자체를 보고하지 않는다. "이제 PM 관점에서 보면" 같은 문장은 순수 낭비다 — 결과물에만 드러나면 된다.

## 11. 제2 저장소 — Obsidian

세션은 끝나면 사라진다. 되풀이될 판단은 볼트에 남겨 다음 세션이 이어받게 한다. `Claude/<역할>/<프로젝트> - <주제>.md`.

**남길 것** — 코드가 말해주지 않는 것:
- 설계 결정과 그 이유 (왜 A가 아니라 B였는지)
- 밟은 함정과 해결 (다음에 또 밟을 것)
- 합의된 범위와 제외 항목
- 보안 점검 결과와 잔여 위험

**남기지 말 것:**
- 코드 구조, 파일 목록 — 저장소를 보면 된다
- 이 대화에서만 의미 있는 임시 상태
- 코드 전문. `file.ts:42`로 가리켜라

**읽기 규칙이 더 중요하다.** 볼트를 통독하면 그 자체가 컨텍스트 낭비다. 같은 프로젝트를 다시 만질 때 해당 역할 폴더를 **Glob으로 제목만** 훑고, 관련 있어 보이는 것 1~2개만 Read.

이미 있는 노트는 새로 만들지 말고 갱신한다. 관련 노트는 `[[이름]]`으로 연결하고, 아직 없는 이름을 걸어도 된다 — 나중에 쓸 것이라는 표시가 된다.

## 12. 판단 기준 한 줄

20% 아래면 더 좁은 호출이 있다는 뜻이다.
