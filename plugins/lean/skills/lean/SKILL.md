# lean — 싸고 빠르게 일하는 법

원칙 하나: **토큰을 아끼는 최선의 방법은 덜 읽는 게 아니라, 처음부터 맞는 것만 읽는 것이다.**
아껴서 헛다리를 짚으면 재작업 비용이 훨씬 크다. 아래 전술은 전부 "정확도를 유지한 채" 비용을 줄이는 것들이다.

## 1. 탐색 — 계단식으로 좁혀라

절대 넓은 Read부터 시작하지 않는다. 순서가 곧 비용이다.

1. **Glob** — 경로/이름으로 후보를 줄인다. `src/**/*auth*.ts`
2. **Grep `files_with_matches`** — 어느 파일인지만 확인. 내용은 아직 받지 않는다.
3. **Grep `content` + `-n` + `-C 3`** — 그 파일들에서 해당 줄 주변만.
4. **Read `offset`/`limit`** — 정말 구조를 봐야 할 때만, 그 구간만.

전체 Read는 파일이 300줄 미만이거나 실제로 전부 고쳐야 할 때만.

**안티패턴**: 파일 5개를 통독한 뒤 그중 1개만 고치기. → 3번까지만 하고 바로 고칠 수 있었다.

## 2. 병렬화 — 속도는 여기서 나온다

의존성 없는 툴 호출은 **한 응답에 전부 묶는다.** 3개를 순차로 부르면 왕복이 3배고, 그 사이 컨텍스트도 3번 커진다.

- 서로 다른 파일 읽기 → 한 번에
- Glob + Grep + `git status` → 한 번에
- 단, 앞 결과가 뒤 인자를 정한다면 순차. 억지 병렬은 헛발질을 부른다.

## 3. 출력을 미리 잘라라

툴 출력은 전부 컨텍스트에 들어간다. 받은 뒤 무시해도 이미 비용은 냈다.

- 셸: `| head -50`, `--max-count`, `git log --oneline -20`, `git diff --stat` 먼저
- 로그/JSON: `jq`로 필요한 필드만
- 테스트: 전체 스위트 대신 해당 파일·케이스 하나만
- 빌드: 성공 여부만 필요하면 출력 억제, 실패했을 때만 다시 자세히

## 4. 셸보다 전용 툴

`grep`/`cat`/`find`/`ls`를 Bash로 부르지 않는다. Grep·Glob·Read 툴이 더 싸고(구조화된 결과) 결과에 파일 링크가 붙는다. Bash는 실제로 셸이 필요할 때만 — git, 빌드, 패키지 매니저, 실행.

## 5. 수정 — Edit가 기본

- 부분 변경은 **Edit**. Write는 새 파일이거나 전면 교체일 때만.
- **고친 파일을 확인차 다시 읽지 않는다.** Edit는 실패하면 에러를 낸다. 성공했다는 건 그대로 적용됐다는 뜻이다.
- 같은 파일을 여러 번 고칠 거면 Edit를 한 응답에 묶어라.

## 6. 캐시를 깨지 마라 (가장 큰 레버)

프롬프트 캐시는 **앞에서부터 이어지는 구간**만 재사용된다. 앞쪽이 바뀌면 그 뒤 전부 다시 만든다.

- 컨텍스트는 **덧붙이는** 방향으로 쌓아라. 이미 읽은 걸 다시 끌어와 순서를 흔들지 마라.
- 세션 중간에 불안정한 대용량 출력(전체 로그, 긴 `ls -R`)을 넣으면 그 뒤가 계속 재생성된다.
- 캐시 적중률이 떨어졌다는 신호가 오면: 새 자료 투입을 멈추고, 지금 들고 있는 것으로 마무리하는 쪽을 택하라.

## 7. 서브에이전트 — 비싸다, 조건을 지켜라

서브에이전트는 **컨텍스트를 처음부터 다시 쌓는다.** 내가 이미 아는 걸 그쪽은 모른다.

쓸 때:
- 파일 수십 개를 훑어야 하는데 **결론만** 필요할 때 (중간 결과를 내 컨텍스트에 안 들이는 게 이득)
- 명백히 독립적이고 병렬로 돌릴 수 있는 큰 덩어리가 여러 개일 때

쓰지 말 것:
- 2~3번의 툴 호출로 끝나는 일
- 내 컨텍스트에 있는 맥락을 길게 설명해야 넘길 수 있는 일 (설명 비용 > 절약분)
- 사용자가 요청하지 않았는데 "꼼꼼히" 하려고

## 8. 답변 자체도 비용이다

- 결론부터. 서론·재요약·"제가 한 일 정리" 금지.
- 방금 보여준 코드나 로그를 답변에 다시 붙여넣지 않는다. `file.ts:42`로 가리켜라.
- 옵션 나열 대신 추천 하나. 사용자가 물으면 그때 대안을 낸다.
- 확인 질문은 **답에 따라 결과물이 실제로 달라질 때만.** 아니면 합리적 기본값으로 진행하고 한 줄로 밝혀라.

## 9. 긴 세션 운용

컨텍스트 점유율에 따라 기어를 바꾼다.

| 점유율 | 방식 |
|---|---|
| ~50% | 평소대로. 필요한 만큼 탐색. |
| 55~75% | 새 파일은 필요한 구간만. 이미 읽은 것 재열람 금지. 탐색보다 마무리 우선. |
| 75%+ | 통독 전면 중단. 지금 작업을 **끝낼 수 있는 단위**로 좁혀 종료하고, 남은 건 새 세션에서. |

75%를 넘겼는데 새 주제를 시작하는 건 최악이다 — 압축이 걸리면서 앞의 맥락을 잃고, 잃은 만큼 다시 읽게 된다.

## 10. 판단 기준 한 줄

의심스러우면 물어라: **"이 툴 호출의 결과 중 실제로 쓸 부분이 몇 퍼센트인가?"**
20% 아래면 더 좁은 호출이 있다는 뜻이다.
